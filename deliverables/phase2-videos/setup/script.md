# Setup & Installation Video — Script (5–10 min)

Audience: someone with no prior exposure who wants to install AIFS/ckptfs and verify it works.
All terminal footage is a **real, unedited run** recorded on Ubuntu 24.04 (FUSE-enabled container): first-time package install, clone from GitHub, build, mount, write, replication, crash/restart. Some footage plays at 0.75–0.9× speed for readability. The Azure NVMe provisioning section is presented as labeled slides (transcript from the README, recorded on real hardware).
Narration: neural TTS (`en-US-AndrewNeural`, −4% rate), stitched sentence-by-sentence with deliberate pauses and loudness-normalized to −16 LUFS; captions carry exact per-sentence timings for a human re-record.

| # | Scene | Visual | Narration |
|---|---|---|---|
| 1 | Intro | `slides/st-01-intro` | In this video, we'll set up the AIFS prototype — ckptfs — going from a clean Ubuntu machine to a working, accelerated checkpoint mount. By the end, you'll have built the filesystem from source, mounted it, written a real checkpoint through it, and watched it replicate to durable storage. Plus — what to do when something goes wrong. |
| 2 | Mental model | `slides/st-02-model` | Before we install anything — the mental model. ckptfs takes three directories. The mountpoint is the virtual filesystem your applications see. Nothing is actually stored there. The spool is fast, local NVMe — every new write lands there first. And the lower directory is your durable storage — an NFS share, in production — which remains the source of truth after a crash. One binary, three paths. That's the whole system. |
| 3 | Prerequisites | `slides/st-03-prereqs` | You'll need a Linux machine — Ubuntu 22.04 or later, or WSL2 on Windows — with sudo access. The toolchain is just four packages: build-essential for the C compiler, fuse3, the libfuse3 development headers, and pkg-config. |
| 4 | Install packages | footage `s01-prereqs` | We start with apt-get update, then install the four packages. On a fresh machine, this takes a minute or two. When it finishes, verify that GCC is available — version 13 here, on Ubuntu 24.04. |
| 5 | Clone & build | footage `s02-clone-build` | Next, clone the repository from GitHub, change into it, and run make. The build takes a few seconds — and produces a single, small binary: ckptfs. |
| 6 | Dirs & launch | footage `s03-dirs-launch` | Now create the three directories — the mountpoint, the durable backend, and the NVMe spool — and take ownership of them. Then launch ckptfs with the three paths, in that order. It runs in the foreground — so keep this terminal open, and do your work in a second one. |
| 7 | Verify & first write | footage `s04-verify-write` | From that second terminal, confirm the mount is live. Then write a test file through it with dd. Notice the speed — that write landed on the local spool immediately. Moments later, the same file appears in the durable backend — together with a hidden marker: .aifs_committed. That marker means the whole checkpoint directory is safely replicated. |
| 8 | Replication demo | footage `s05-watch-replication` | Now — the real workflow. We save a multi-file training checkpoint — model, optimizer, scheduler, RNG state — while refreshing both directory listings five times a second. The spool on the left fills instantly. A training job would already be unblocked. On the right, the background replicator copies each file over, in order — and the commit marker arrives last, sealing the checkpoint. On real hardware with an NFS backend, that right-hand column trails by thirty to forty seconds. And the GPUs never wait for it. |
| 9 | Crash & restart | footage `s06-recovery` | So — what about crashes? We kill ckptfs mid-flight, and restart it. On startup, the old spool is quarantined — never trusted after a crash. But the durable backend still holds every committed checkpoint. The recovery rule is simple: resume training from the newest checkpoint that carries the commit marker. |
| 10 | Real NVMe (Azure) | `slides/st-04-azure` | One note — this demo ran in a container, so both tiers shared a single disk. On a real cloud VM, you'd first provision the local NVMe disk: partition it with fdisk, format it ext4, and mount it. The full transcript is in the README, recorded on an Azure L8as_v3. One warning before you use the bundled setup script: it force-formats the first NVMe device it finds — and on many VMs, that's the OS disk. Always check the device name first. |
| 11 | Measured results | `slides/st-05-benchmark` | Set up this way on real hardware, the prototype sustained 879 megabytes per second, on the fully durable path. That's a four-gibibyte checkpoint, locally safe in under five seconds — with replication completing off the critical path, about half a minute later. |
| 12 | Troubleshooting | `slides/st-06-troubleshoot` | Finally — the issues you're most likely to hit. If the mount is dead after a crash, unmount it with fusermount3 -u before relaunching. If ls on the mount shows nothing after a restart — that's a known prototype limitation. Your data is still safe, in the backend. Write checkpoints into their own directories — never loose files at the mount root — or commit markers won't work. And clean up quarantined orphan spool directories from time to time. They're never deleted automatically. |
| 13 | Recap | `slides/st-07-recap` | And that's the whole setup. Four packages, one make, three directories, one command. The full install guide and troubleshooting notes live in the repository, under deliverables. Try it against your own training pipeline — and stop paying the checkpoint tax. |
